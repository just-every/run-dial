# Destructive personal erasure

Implementation candidate with native route, migration and CLI evidence below. Complete deployment-wide erasure remains blocked by the native rate-attribution boundary; the verified local SDK retention fix is integrated. This document distinguishes verified behavior from remaining work. It supersedes the pinned 91c27cd draft census in an earlier private draft.

The migrated schema has **110 application tables, eight static portability tables and SQLite's sqlite_sequence**: 119 tables before runtime-created copies or platform metadata. This includes auth 0030/0031, avatar 0032, Unicode search 0033, custom fields 0034, additive erasure 0035/0036 (0036 adds anonymous retention status and identity-admission guards, with no new table), the erasure scope and rate correlation tables 0037/0038, and move-in capture facts 0040. `booking_search_casefold` is included in the application census and classified as non-personal normative data; archive policy treats it as destination-installed internal data. This corrects the historical 53-table statement.

## Operator flow and guarantees

Settings → Erase personal data accepts an email, returns case-insensitive booking/request counts and a five-minute session-bound confirmation without writes, and accepts one confirmation. A success returns one anonymous aggregate receipt: counts, requested/completed times, local completion, associated-operator-retained status and remote calendar state. No original IDs, actor, email or free text are in that receipt. Shared per-entity receipts retain anonymous table counts only when complete. No fake provider completion is recorded.

Local native rows, portability tombstones, transfer invalidation, anonymous audit and imported custody commit together for each erased entity. All entities finish before the request returns success. A failure can leave earlier entities erased; no aggregate completion is reported. Address admission remains closed and the operator can preview the remaining records and resume. Export refuses an incomplete operation or admission lock. This is resumable destructive work, not an all-person rollback promise. Authority is checked at admission and at the end of each native deletion batch; imported custody also uses its maintained final authority guard.

New matching bookings, request reviews, requests and mail are refused during person erasure. Snapshot creation and restore publication are refused while an erasure admission exists. An already-applying restore prevents erasure from starting. Each entity uses the maintained graph to discover and fence every native row before explicitly deleting children; FK cascades are no longer relied upon for unfenced native deletion. Unknown tables and missing migrated tables stop erasure before personal deletion.

Person/operator overlap permits the same single confirmation to erase every matching booking/request and address remainder. Preview and completion receipt explicitly report that the associated operator identity is retained; this includes the acting operator and protected setup owner. The person action preserves native accounts, sessions, auth links and setup authority, and removes matching actor references from anonymized invitee audit. New native/product identities and true address changes into the admitted email are fenced; unchanged identity writes remain allowed, and the receipt locks retained identities against changing address during deletion. Auth identity and sign-in data remain governed by the separate account-removal action. After invitee cleanup, a non-protected operator can be removed separately in Operator access. The operator removal route also holds while matching invitee records exist; it never claims full identity removal while retaining that personal identity as an invitee. Self-removal and setup/bootstrap-owner removal are held, and Base's native last-owner trigger remains active. Dial has no owner-transfer workflow yet; that is the explicit protected-owner path required before erasure. Ordinary operator removal deletes the native identity, auth/link sessions, local mail and computable email-rate keys, retaining only a product author stub `erased:<opaque id>` and unrelated authored facts. A native valid-link confirmation rate key can remain because the maintained authentication API has no atomic attribution hook; full identity erasure therefore remains incomplete. A later invitation creates a fresh native identity. An inactive identity whose erasure failed remains visible for retry.

## Contract replacement

EVENT-005 deliberately supersedes BASE-DATA-003's event-type cascade: deleting or disabling public event configuration does not destroy historical bookings, private manage links or managed calendar events. DATA-002 already promised that erasing every matching booking/request erases the person from the deployment. Its revised wording adds explicit email preview/confirmation, receipt, partial-failure and restore-fence behavior. The person action now explicitly retains associated operator identity under OPER-002 instead of blocking invitee cleanup; full identity erasure remains unavailable for protected owners and incomplete at the native rate-attribution boundary. No deployment-wide DATA-002 completion is claimed. CUSTOM-002 sidecar values follow booking/request erasure; event-type annotations remain host configuration. OPER-002 now describes destructive identity removal and its holds rather than the earlier access-only removal/self-removal policy. The original event-type noncascade remains unchanged.

E = exported; X = excluded; N = destination-installed/platform internal. A personal classification includes pseudonymous links, capabilities and provider identifiers. Host data is personal to the host, not automatically owned by every invitee or operator sharing it.
