# Destructive personal erasure

Implementation candidate with native route, migration and CLI evidence below. The native rate-attribution gap is closed; deployment-wide erasure is not claimed because physical SQLite sanitization, external provider/log copies and deployed acceptance remain unproved. The verified local SDK retention fix is integrated. This document distinguishes verified behavior from remaining work. It supersedes the pinned 91c27cd draft census in an earlier private draft.

The migrated schema census has **151 application tables, eight static portability tables and SQLite's `sqlite_sequence`**: 160 tables before runtime-created copies or platform metadata, after 72 core migrations (0071 adds a receipt column, no table; 0072 adds invitee guests; 0073 adds approval requests and tokens). This includes auth 0030/0031, avatar 0032, Unicode search 0033, custom fields 0034, additive erasure 0035/0036, erasure scope and rate correlation 0037/0038, import-custody retirement 0041, hosted portability 0043, local dependency setup 0044, import preparation steps and stream sources 0045/0046, availability controls 0055, booking policy 0056, correspondence 0057, reschedule requests 0058, event locations 0060, booking links and offered times 0061/0062, confirmation and invitation controls 0063–0065, connection-health history 0066, request browser zones 0067, Stripe payments 0068, deposits, refunds and fees 0069, sales tax, receipts and invoices 0070 the erasure receipt's Stripe customer count 0071 invitee guests 0072 and host-approval requests 0073. `booking_search_casefold` is included in the application census and classified as non-personal normative data; archive policy treats it as destination-installed internal data. This corrects the historical 53-table statement.

## Operator flow and guarantees

Settings → Erase personal data accepts an email, returns case-insensitive booking/request counts and a five-minute session-bound confirmation without writes, and accepts one confirmation. A success returns one anonymous aggregate receipt: counts, requested/completed times, local completion, associated-operator-retained status and remote calendar state. No original IDs, actor, email or free text are in that receipt. Shared per-entity receipts retain anonymous table counts only when complete. No fake provider completion is recorded.

Local native rows, portability tombstones, transfer invalidation, anonymous audit and imported custody commit together for each erased entity. All entities finish before the request returns success. A failure can leave earlier entities erased; no aggregate completion is reported. Address admission remains closed and the operator can preview the remaining records and resume. Export refuses an incomplete operation or admission lock. This is resumable destructive work, not an all-person rollback promise. Authority is checked at admission and at the end of each native deletion batch; imported custody also uses its maintained final authority guard.

New matching bookings, request reviews, requests and mail are refused during person erasure. Snapshot creation and restore publication are refused while an erasure admission exists. An already-applying restore prevents erasure from starting. Each entity uses the maintained graph to discover and fence every native row before explicitly deleting children; FK cascades are no longer relied upon for unfenced native deletion. Unknown tables and missing migrated tables stop erasure before personal deletion.

Person/operator overlap permits the same single confirmation to erase every matching booking/request and address remainder. Preview and completion receipt explicitly report that the associated operator identity is retained; this includes the acting operator and protected setup owner. The person action preserves native accounts, sessions, auth links and setup authority, and removes matching actor references from anonymized invitee audit. New native/product identities and true address changes into the admitted email are fenced; unchanged identity writes remain allowed, and the receipt locks retained identities against changing address during deletion. Auth identity and sign-in data remain governed by the separate account-removal action. After invitee cleanup, a non-protected operator can be removed separately in Operator access. The operator removal route also holds while matching invitee records exist; it never claims full identity removal while retaining that personal identity as an invitee. Self-removal and setup/bootstrap-owner removal are held, and Base's native last-owner trigger remains active. Dial has no owner-transfer workflow yet; that is the explicit protected-owner path required before erasure. Ordinary operator removal deletes the native identity, auth/link sessions, local mail and computable email-rate keys, retaining only a product author stub `erased:<opaque id>` and unrelated authored facts. Known-operator email and valid-link counters are correlated atomically and removed with the operator; migration 0039 retires pre-correlation counters. A later invitation creates a fresh native identity. An inactive identity whose erasure failed remains visible for retry.

## Contract replacement

EVENT-005 deliberately supersedes BASE-DATA-003's event-type cascade: deleting or disabling public event configuration does not destroy historical bookings, private manage links or managed calendar events. DATA-002 already promised that erasing every matching booking/request erases the person from the deployment. Its revised wording adds explicit email preview/confirmation, receipt, partial-failure and restore-fence behavior. The person action now explicitly retains associated operator identity under OPER-002 instead of blocking invitee cleanup. Self/setup/last-owner removal remains held, and no deployment-wide DATA-002 completion is claimed. CUSTOM-002 sidecar values follow booking/request erasure; event-type annotations remain host configuration. OPER-002 now describes destructive identity removal and its holds rather than the earlier access-only removal/self-removal policy. The original event-type noncascade remains unchanged.

## Paths and census

Availability controls added in migration 0055 retain `availability_schedules`, `event_schedule_bindings` and `booking_limit_policies` as shared host configuration (H), exported (E). They contain no invitee identity or booking answers; invitee erasure leaves them intact. Their persisted JSON is validated on archive restore.

Migration 0056 retains `event_booking_policies` as exported host configuration (H/E). `booking_presentation` holds a booking's locked display zone and nullable browser zone (B/E): the booking graph explicitly discovers, fences and deletes it, and its booking foreign key also cascades on deletion. Restore requires canonical IANA zones (including UTC), nullable integer policy values from 0 to 2147483647, and existing event/booking references. It preserves an unlocked event policy as a null lock; presentation rows always require a locked zone.

Migration 0063 adds the default-on invitee confirmation setting to the existing correspondence JSON. It follows event configuration duplication and archive validation; retained booking copies follow booking erasure. A skipped confirmation retains its private capability and a `confirmationSuppressed` marker in the existing delivery payload, erased with that delivery. No new personal-data table is introduced.

Migration 0057 retains `event_correspondence` as exported host configuration (H/E). `booking_correspondence` is an exported per-booking template snapshot (B/E), explicitly discovered, fenced and deleted with the booking; its booking FK also cascades. Restore validates the complete ten-field template configuration, nullable strings, title/subject and body bounds, variable names and brace grammar, and the calendar prohibition on manage links. Native editing additionally validates current question existence and privacy; archive validation does not reinterpret historical snapshots against current question metadata.

Move-in undo includes event schedule bindings, event-scoped booking limits, event booking policies and event correspondence in exact event custody, and presentation and correspondence snapshots in booking custody. A later owner edit prevents removal of that imported entity. Empty additive sidecars are absent from custody snapshots, preserving historical applied hashes; nonempty sidecars include every persisted column.

B = booking graph; Q = request graph; P = final email remainders; O = operator identity graph; I = maintained import-kit erasure with `withdraw-all-job-artifacts`; T = maintained portability transfer invalidation; H = retained shared host/configuration; A = anonymous receipt/audit; F = intentional opaque anti-replay fence. E = exported; X = excluded; N = destination-installed/platform internal. A personal classification includes pseudonymous links, capabilities and provider identifiers. Host data is personal to the host, not automatically owned by every invitee or operator sharing it.

## Payments custody (PAY-001, PAY-003)

Dial stores no card data. A booking's payments keep only amounts, the connected account ID and Stripe references; a saved card for stated fees keeps only the Stripe customer and payment-method references beside the invitee's consent (wording version, time and the fee amounts shown). Erasing a payer's booking first asks Stripe to detach the saved payment method, when the deployment's Stripe connection is live, and records the outcome in the anonymized audit (`saved_card_detached`, or the refusal reason) and on a person erasure's receipt (`savedCardsDetached`, `savedCardFailures`). The booking's consent, card references, terms snapshot, balance link and money movements are then deleted with it. Each payment and money movement survives only in the anonymized audit with its kind, status, actor type, time, amount and Stripe reference, which keeps the accounting trail that `BASE-DATA-003` requires without any payer detail.

Gap: when the Stripe connection is missing, disconnected or deauthorized at erasure time, or Stripe refuses, Dial cannot ask Stripe to detach the card. Dial still deletes its own references, and the receipt counts the card under `savedCardFailures`; the card then stays attached to the Stripe customer in the host's own Stripe account until the host removes it there. Archives carry payment terms, consents (Stripe references only), movements, payments and payment settings; balance-link capabilities never travel. Receipts and invoice emails are booking mail in the delivery outbox and are erased with the booking or by recipient like other mail. Dial sends a billing address to Stripe Tax and to Stripe when it creates an invoice's customer, and keeps only the tax figures and jurisdiction summary. Stripe customer objects that Checkout creates for a saved card, or that Dial creates for an invoice, stay in the host's own Stripe account with the payer's email, name and any billing address; erasure deletes Dial's references but does not delete those Stripe customers, which the host removes in Stripe. A person erasure's receipt counts them as `stripeCustomersRetained`: for each erased booking, the saved-card customer on its card consent plus one customer for each invoice Dial issued for it (each issue asks Stripe to create one), read before the rows are deleted; a receipt made before migration 0071 reads `null` (not counted). When the count is above zero the receipt says: "These Stripe customers remain in the host's Stripe account with the payer's email, name and any billing address; remove them in Stripe." It also counts saved cards Stripe detached (`savedCardsDetached`) and those not detached (`savedCardFailures`).
