- `NOTIFY-007`: every calendar failure the connection health check can see now alerts within 60 seconds of its onset, from the moment a calendar is connected, and brief errors never alert. The connection watch's probe makes the health check's own two reads (the destination calendar lookup and a free/busy read over the conflict calendars) instead of the lookup alone, so a conflict calendar that is unshared or deleted alerts 49.3 s after onset at the slowest phase instead of 79.3 s. The probe runs 30 s after each healthy check rather than on each minute and half minute, so it no longer repeats the scheduled pass's reads: provider calls stay at 5,760 connection-check calls a day per connection (2,880 destination lookups and 2,880 free/busy reads; before, 4,320 lookups and 1,440 free/busy reads), plus an hourly token refresh. The watch starts when a connection reads healthy (connect, reconnect or re-authorise) instead of at the next scheduled pass, so a failure in the first minute alerts 51.0 s after onset instead of 79.2 s. A sighting on a healthy connection starts an incident that is re-checked 10 s and confirmed 20 s later; a re-check that reads healthy ends it, and the confirmation alerts only if the connection stayed unhealthy since the sighting. A second brief error that spans an earlier error's confirmation no longer sends an alert and a recovery notice. `node scripts/lifecycle/connection-alert-timing.mjs` now also times the conflict-calendar and first-minute failures and runs the two-brief-errors case; journey step 6c's unseen incident is now a conflict-calendar failure.
- `NOTIFY-007`: a persistent calendar failure alerts within 60 seconds of its onset, even when no request sees it. While a calendar connection exists, a Durable Object alarm probes the destination calendar on each minute and half minute of the clock: one calendar lookup, 2,880 Calendar API calls a day per connection on top of the one-minute pass's 2,880 (about 5,760 a day in all, plus an hourly token refresh). A request, pass or probe that first sees a healthy connection fail schedules a confirmation check 20 s later (previously 25 s), and that check is the only path that alerts on an unhealthy calendar. A failure that persists alerts once per incident, at most about 50 s after it starts; a brief error that recovers before the check sends nothing, including one that spans the one-minute scheduled pass (which used to alert on the spot and then announce recovery). Before, a failure that started just after the pass and that no request saw alerted about 85 s later. The lifecycle journey times a brief error across the pass, a persistent error, a second failure in the same incident and a new incident no request sees, measured from its onset; `node scripts/lifecycle/connection-alert-timing.mjs` times failures that start at chosen phases of the minute.

## 0.1.0 — first release

- Single-host scheduling with public booking, private manage links, alternative requests and operator workspace.
- Server-rendered public React documents with native Hono API and session boundaries.
- Calendar provider v2, public admission and blocking, notification preferences, and recoverable operator booking creation.
- Pinned Base operator authentication, transactional mail and deployment components; durable notification and SendGrid invocation custody.
- Event configuration revisions advance atomically even when the clock stalls or moves backwards. Concurrent changes, including date overrides, reject stale publication and in-flight booking-link copy reports; failed writes retain the prior configuration.
- Explicit request-only publication with verified mail and a saved host profile while calendar setup is pending; automatic booking keeps its full readiness checks.
- Day-first time selection groups valid weekly slots by invitee date and keeps ranked suggestions first within the selected day; PUBLIC-001 and AVAIL-005 record the presentation change without changing privacy guarantees.
- Operations checks enforce a no-reply sender and explain how to correct its configuration.
- The repository includes the owner-session dispatcher with an offline dry-run for every supported command.
- Branded multipart booking, reschedule, cancellation, reminder, acknowledgement and operator mail; reminders retain the 24-hour and 1-hour schedule.
- Private local and remote data archives restore only into a migrated empty install, exclude credentials and live capabilities, preserve original assets and durable facts, and prevent historical provider effects from replaying. Use `pnpm run import` for restore.
- Base local setup and bounded development outbox, branded sign-in/confirmation pages and mail, and plain operations input summaries.
- First-run setup tracks native authenticated booking-link copy reports, invalidated when relevant event or host identity details change.
- Deployed-install fixes found by the disposable-install run: export recognises D1's platform key-value table and Cloudflare's response for a bucket with no objects, and platform health marks each primitive independently under a five-second deadline instead of failing all three when one is slow.
- A public product landing at `/` in Dial's own look (Figtree, warm paper, ink and gold, an inline dial drawing with a one-shot hero motion), sharing its header, footer and type with a restyled `/docs`; HOME-001 records the sections, the host booking-profile link when a profile exists, the owner identity, the optional credit and the same-origin, cookie-free page. The Dial mark and favicon are redrawn for every surface.
- First-party documentation at `/docs`, rendered at build time from the repository's Markdown and published by `docs/site.json`; DOCS-001 records the sessionless, cookie-free, GET-only page and its share of the public admission budget.
- Ordered migrations 0001–0025. Migration 0016 requires operators to sign in again after upgrading from legacy authentication.

EVENT-006 adds an explicit request-only publication exception and calendar-optional fixed-location booking. Publishing enables real bookings; setup and publication now disclose that disconnected events do not check external calendar conflicts. The connected-calendar journey also refuses confirmation during an outage without creating booking or delivery side effects. Public extension points are unchanged. See [RELEASE.json](RELEASE.json) for migration instructions and [HANDOVER.md](HANDOVER.md) for unverified acceptance obligations. Live Google Calendar acceptance remains outstanding; no tag or public publication is claimed.
