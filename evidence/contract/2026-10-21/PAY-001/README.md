# PAY-001 evidence (21 October 2026)

- `*-1440.png`, `*-390.png`: Settings (Stripe connected), the event-type price field, the pay step, the payment return while Stripe has not confirmed, the receipt, the manage page and the operator booking record, from `scripts/verify-payment-screens.mjs` on the review rig with Stripe synthetic at the HTTP edge.
- `stripe-test-mode.json`: one local run of `scripts/verify-payment-stripe-test-mode.mjs` against api.stripe.com in TEST mode through the fleet key door. Dial's own confirm route created a real Checkout Session; test card 4242 paid on Stripe's hosted page in headless Chromium; the return URL confirmed nothing; the real `checkout.session.completed` from `GET /v1/events` was delivered to Dial's webhook signed with a throwaway endpoint's secret (a mis-signed copy was 401, a duplicate added nothing); Dial's sweep expired a second real session and freed its slot. Cleanup readbacks: the webhook endpoint deleted (none listed), no open session, the charge refunded. No customer was created: neither Dial nor the harness calls Stripe's Customer API, and this line is by construction, not a readback.
- Not proven here: Stripe-to-Dial delivery (the local Worker is unreachable from Stripe), a real Connect OAuth grant (no Connect client ID; this test account has no Connect platform, so the platform account was addressed through the `Stripe-Account` header and the harness added the `account` field a Connect delivery carries), and a live ACH payment. The sandbox Worker runtime had no direct egress, so a local forwarder relayed Dial's request bytes unchanged.
- Found by the real run and fixed in this change: Stripe now refuses `payment_method_types` on Checkout Sessions; methods come from the account's Dashboard settings and ACH is excluded unless the host enables it.

No key, session secret or webhook secret is stored here.
