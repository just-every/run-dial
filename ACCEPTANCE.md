# Dial acceptance

Start with the jobs a new host and invitee need to complete:

- The host signs in, saves a profile and timezone, creates an event with a private location, sets weekly availability, publishes it and copies its booking link.
- An invitee opens that link without an account, picks a time in their own zone, confirms with a name and email, and gets the location, an add-to-calendar file and a private manage link.
- The invitee reschedules or cancels through that private link, and the host sees the change in Bookings, with list times in the host's named zone.
- An invitee requests another time; the host reads the windows in both zones and creates the agreed booking from the request.
- On a hosted install, deploy claims the owner and the owner signs in by email link. Working mail and a readable owner mailbox are prerequisites. The owner can export their data and remove the deployment using the documented commands.

The checks and provider limits below support those jobs.

The target contract widens those jobs to the whole scheduling category; a build round works towards these through the ledger below:

- A team admin invites hosts, connects each host's Google, Microsoft 365 or iCloud calendars and Zoom or Teams, publishes round-robin, collective and group events from a managed template, and sees fair distribution.
- A website visitor fills a routing form, is routed by their answers or their CRM owner to the right host, pays a deposit through the host's Stripe or PayPal, and gets email and consented SMS reminders.
- After the meeting, attendance is established, a no-show is recovered under the host's policy, and the agreed follow-up is drafted for the host to approve; HubSpot, Salesforce or Orbit and Slack see the outcome.
- An owner moves in from Calendly, Acuity Scheduling or Microsoft Bookings, including teams, routing, workflows and future bookings, without notifying anyone again, and cuts over every old link.


The release candidate must preserve every requirement in [CONTRACT.md](CONTRACT.md) and [BASELINE.md](BASELINE.md), including deliberate supersessions described in [DIVERGENCE.md](DIVERGENCE.md). The manifest's maturity, capacity estimates and accessibility target remain explicit limits on claims.

## Parts 1–4: bounded local acceptance

The first four acceptance parts have bounded local evidence for avatar handling, booking filters, Unicode search and private annotations. This evidence covers local product behavior only; it does not establish the complete release gate.

`PROFILE-003` avatar upload is implemented with migration `0032_host_avatar.sql`. The native route requires an operator session, validates the upload size and file signature, and writes to a generated R2 key. From Profile, an operator can upload or replace the picture, or remove it; removal deletes that avatar object while preserving unrelated R2 objects. Only the current avatar is served from `/media/`, inline with its declared content type, `nosniff`, and no cookie. The archive path preserves original object bytes and content type. These are local Worker and archive-path results, not deployed media acceptance.

`OPER-003` filters combine lifecycle state, future or past start time, event type, date range, and external-delivery failure. The workspace keeps the controls in the URL, sorts by start instant, and renders result counts and the empty state. Search is a literal, full Unicode case-insensitive substring over invitee name and email. Migration `0033_booking_search.sql` adds and maintains folded search values. A reopened local D1 containing 100,000 bookings and 10,000 failed-delivery rows was measured over 20 filter/search cases, with 20 samples per case after two warmups. Broad search at the default 500-row page size measured p50 162.2 ms and p95 230.9 ms; combined filters plus search measured p50 96.4 ms and p95 334.3 ms, the highest p95 in that run. Every case's p95 was below 500 ms, but individual samples reached 535.1 ms for combined filters plus search, 789.1 ms for date range, and 896.8 ms for excluding failed deliveries. These measurements describe that local database and workload; production capacity remains unproved.

A follow-up native timing review on `d7ba20d` reopened the 100,000-booking/10,000-failed-delivery D1 and collected 120 interleaved HTTP samples while observing real D1 calls. Combined filters plus search (60 samples) measured p50/p95/maximum 78.370/85.437/110.135 ms; broad search at the default 500-row limit (20 samples) measured 123.138/135.078/137.672 ms. The remaining date-range and no-failed-delivery groups (20 samples each) had maxima of 144.915 ms and 147.966 ms. None of these 120 follow-up samples exceeded 500 ms. The review has not established a cause for the earlier outliers; no machine-noise attribution or production-capacity claim is made. Raw local timing records are in the evidence folder (`PERFORMANCE.md` and `gate-parts14-performance.json`), which is not included in a fresh clone.
